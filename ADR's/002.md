ADR 002: Model the compliance obligation separately from the certificate document
Status: accepted
Date: 2026-10-19
Context

Every managed property is legally required to hold a current certificate of each type the agency is responsible for: gas safety, EICR, EPC, and in some cases legionella and fire risk.

Two things need representing, and they are not the same thing:

The requirement itself, which exists from the moment a property comes under management, whether or not any certificate has ever been produced for it.
The actual files received, of which there may be several for one requirement: a landlord sends the wrong document, sends it twice, has it rejected and sends a corrected one, or renews it annually for years.

The system's main job is chasing, which means it has to track the state of a requirement that has no document attached to it yet.

Decision

Two tables.

compliance_item is the obligation. One row per property per certificate type, enforced by a unique index on (property_id, type). It carries the state machine: current, chasing, waiting, in_review, escalated, ended.

certificate_document is each file received. Many rows per obligation, each with its own storage key, content hash, extracted data and review state.

Alternatives considered

One table, where a row is a certificate. Rejected, and this was the deciding argument. A property that has never had a gas certificate has no document, so there is no row to mark as chasing. The system would not even know the obligation exists. Working around that means inserting placeholder rows with every field null, which is the obligation table with a worse name and no constraints.

One table, where a row is the obligation and the document is a set of columns on it. Rejected. An obligation receives many documents over its life and all of them must be retained. Rejected submissions are evidence that the agency chased correctly and the landlord sent the wrong thing, which matters precisely when something has gone wrong. Overwriting the document columns on each submission destroys the audit trail the product is sold on.

Obligation, document, and a separate submission or attempt table. Rejected as premature. The extra layer buys nothing that certificate_document with a received_at and a review_state does not already give, and it adds a join to the review queue.

Consequences

The state machine sits in the right place. chasing, waiting and escalated are states of an obligation, not of a file, and now they have a row to live on. Review state (pending, approved, rejected, unreadable) sits on the document, because being approved or rejected is a property of a submission. These two state fields are deliberately separate and must not be collapsed.

Expiry is stored in two places. The authoritative expiry lives on the approved document. A copy lives on compliance_item so the dashboard reads one table in index order with no join and no sort. This is a deliberate denormalisation, covered in ADR 003, and it means approving a document is a two-table write that must happen inside one transaction.

Approval is transactional or it is wrong. The approve path marks the document approved and updates the obligation's expiry and state. If the second write does not happen, the dashboard shows stale data and the system chases a landlord who has already complied. Nothing in the database prevents that, so it is enforced by a transaction and covered by a test.

Accepted limitation: one landlord per property. property.landlord_id is a single non-null column, so jointly owned properties cannot name both owners. This is common in reality. In v1, staff work around it by searching the other partner's name when a search comes up empty. Supporting it properly needs a join table and a rule for who receives each chaser, and it is an additive migration later rather than a rewrite, so it is deferred rather than designed around now.

Accepted decision: ON DELETE no action on every foreign key. Postgres will refuse to delete an agency, landlord or property that still has rows depending on it. cascade was rejected deliberately: a single mistyped delete would silently destroy six years of compliance evidence with no error and no recovery. Removing an agency's data is instead an explicit sequence in reverse dependency order, inside one transaction, that can be reviewed and audited. The cost is that deletion is more work to write, which is the correct side to err on for a product whose value is its evidence trail.
